# BionicPRO

Проектная работа 9-го спринта: безопасный вход и получение отчётов о работе собственных протезов. Приложение использует React / TypeScript, Keycloak 21.1, PostgreSQL 14, Apache Airflow 3.4.0, ClickHouse 26.8.36.3 и API на Python / FastAPI.

## Архитектура и границы реализации

В целевой архитектуре **BFF** — серверная часть для клиентских приложений — получает и обновляет токены **IdP** (удостоверяющей службы). Браузер использует непрозрачную сессионную cookie с `Secure`, `HttpOnly` и `SameSite`; для запросов предусмотрена защита от CSRF. Keycloak подключает внешние каталоги LDAP/AD и службы OIDC/SAML. Для каждой страны предусмотрены отдельные установки и локальное хранение учётных, персональных и медицинских данных, сессий, журналов и резервных копий. Страны A и B на схеме обозначают варианты размещения.

Практическая часть задачи 1.2 дорабатывает исходное приложение **React → Keycloak**: Authorization Code Flow дополнен PKCE `S256`. Токены получает JavaScript-адаптер; код приложения не сохраняет их в localStorage или sessionStorage. PKCE защищает обмен кода на токен, но не переносит токены на сервер. BFF, внешние IdP и региональное развёртывание представлены в архитектуре; в локальный Docker Compose они не включены. Файл `ldap/config.ldif` сохранён из исходного репозитория, LDAP-сервис в стенде не запускается.

Сервис отчётов реализует контейнер **API** исходной схемы. Поток данных:

1. CRM хранит связь клиента с учётной записью и принадлежность протезов. Отдельная PostgreSQL хранит телеметрию.
2. Airflow выполняет **ETL**: извлекает данные, проверяет их, объединяет и рассчитывает дневные показатели.
3. ClickHouse хранит **витрину** — отдельную таблицу с готовыми показателями — и реестр опубликованных дней.
4. API проверяет пользователя и готовность всего периода, затем читает собственные строки пользователя из витрины.
5. React передаёт даты и скачивает JSON. Запрос отчёта не запускает DAG и не пересчитывает сырые события.

Схемы draw.io содержат по две вкладки. `security.drawio` описывает управление доступом и размещение, `reporting.drawio` — подготовку и выдачу отчётов. Поток локального стенда отличается от целевой схемы наличием access-токена в React вместо BFF.

## Модель данных и подготовка отчёта

CRM в стенде представлена таблицами PostgreSQL с синтетическими данными. Это учебный источник, а не установка Битрикс24. Для реальной CRM нужен адаптер к её поддерживаемому интерфейсу. Поля, суточная детализация и JSON-формат выбраны для проекта.

| Хранилище | Данные |
|---|---|
| `crm.clients` | Клиент и уникальная пара `(owner_issuer, owner_subject)` — идентификатор удостоверяющей службы и пользователя. |
| `crm.prostheses` | Протез, его клиент-владелец и модель. У клиента может быть несколько протезов. |
| `telemetry.movement_events` | `event_id` — движение; `ingestion_id` — доставка сообщения; протез, время события UTC и время реакции в миллисекундах. |
| `reports.daily_prosthesis_usage` | Владелец, клиент, протез, модель из CRM, день UTC, число движений, среднее время реакции и версия публикации. |
| `reports.report_publications` | День, опубликованная версия, время публикации и контрольные счётчики. |
| `reports.ready_periods` | Представление, выбирающее последнюю опубликованную версию каждого дня. |

Индивидуальный протез закреплён за одним клиентом. Переназначение владельца в учебной модели не предусмотрено; для него потребуется история владения. Отсутствие телеметрии не доказывает отсутствие движений: пользователь может отключить её отправку.

### DAG и публикация

DAG `bionicpro_daily_reports` содержит шесть задач:

```text
select_interval → [extract_crm, extract_telemetry] → build_mart → load_version → publish_period
```

Расписание — ежедневно в **00:00 UTC**, за предыдущий завершённый день. `CronDataIntervalTimetable` задаёт интервал `[00:00, следующие 00:00)`. `catchup=False` отключает автоматическую обработку всей истории. Для конкретного дня передаётся параметр `report_date`. `max_active_runs=1` ограничивает публикацию одним запуском DAG; чтение двух источников выполняется параллельно. У задач две повторные попытки с задержкой 30 секунд.

- CRM читается в согласованном снимке PostgreSQL. События читаются потоком с сортировкой по `event_id`.
- Точные повторные доставки учитываются один раз. Конфликт одного `event_id`, неизвестный протез или неоднозначный владелец останавливают публикацию.
- Дневные показатели рассчитываются по клиенту и протезу. В ClickHouse записывается новая версия, затем проверяются число строк, уникальные ключи и сумма движений.
- Только после проверки создаётся запись в реестре готовности. Для дня без событий она тоже создаётся.
- При повторной обработке используется новый `publication_id`. API читает только опубликованные версии; старые строки не суммируются с новыми. Если публикация произошла между двумя чтениями API, запрос использует версии, выбранные при первом чтении.

Ключ сортировки витрины начинается с владельца и даты. Ключ MergeTree не обеспечивает уникальность: повторяемость загрузки обеспечивает логика версий. Роли `crm_reader` и `telemetry_reader` читают источники; `etl_writer` читает и добавляет данные ClickHouse; `reports_reader` только читает их.

В XCom передаются пути и небольшие метаданные. Файлы промежуточных данных находятся в томе `airflow_work` и доступны задачам локального исполнителя. Для распределённого Airflow потребуется общее хранилище в той же стране. Автоматическая очистка промежуточных файлов и старых версий в стенде не настроена; удаление опубликованных версий должно учитывать незавершённые запросы API.

## Локальный запуск

Нужны Docker Desktop с Docker Compose и Python 3.9+ для вспомогательных скриптов. Все команды выполняются из корня репозитория. Пакеты Python на хост устанавливать не требуется; backend и Airflow работают в контейнерах. Сервисы отчётности объединены в профиль `reports`; при явном указании сервиса Compose включает его автоматически.

### 1. Keycloak

```bash
docker compose config --quiet
docker compose up -d keycloak
docker compose ps keycloak keycloak_db
```

При первом запуске дождитесь ответа [конфигурации realm](http://localhost:8080/realms/reports-realm/.well-known/openid-configuration). Затем примените настройки клиента:

```bash
docker compose exec -T keycloak bash -s < keycloak/enable-pkce.sh
python3 keycloak/configure-reports-api.py
```

Первый скрипт включает обязательный PKCE `S256`, Standard Flow и отключает Implicit Flow / Direct Access Grants. Второй добавляет audience `reports-api` в access-токен и адрес входа Swagger UI. Скрипты используют учётные данные администратора внутри контейнера, сохраняют пользователей и допускают повторный запуск. При `--import-realm` существующий realm пропускается, поэтому одного изменения JSON и перезапуска недостаточно.

Учебные пользователи `user1` и `user2` и их пароли заданы в `keycloak/realm-export.json`. Пароли в репозитории и Compose — демонстрационные значения для локального стенда. `frontend/.env` содержит только адреса сервисов, realm и публичный идентификатор клиента.

### 2. Источники и ClickHouse

```bash
docker compose up -d --wait crm_db telemetry_db clickhouse
python3 scripts/seed_demo.py --day 2026-11-10
```

Загрузчик связывает CRM с действующими идентификаторами `user1` / `user2` из Keycloak и заполняет только источники. Повтор с той же датой не перезаписывает данные и не добавляет дубли. Витрину и реестр готовности заполняет DAG.

SQL из `docker-entrypoint-initdb.d` выполняется только при первом создании тома. Изменения схемы существующей БД требуют миграции, а не удаления тома. Порты источников не публикуются; ClickHouse доступен с хоста по `127.0.0.1:8123`.

Параметр `--day` — последний завершённый день учебного набора. При другой дате набор смещается; для проверок ниже используется `2026-11-10`.

| День UTC | Принятых сообщений | Уникальных движений |
|---|---:|---:|
| 2026-11-08 | 3 | 3 |
| 2026-11-09 | 0 | 0 |
| 2026-11-10 | 9 | 8 |

У `user1` два протеза, у `user2` один. Дополнительное сообщение 10 ноября — повторная доставка одного движения. Пустой день не появляется в группировке исходных событий; его готовность подтверждает реестр публикаций.

### 3. Airflow и обработка дней

```bash
docker compose up -d --build --wait airflow
docker compose exec -T airflow airflow dags list-import-errors
```

Ожидаются состояние `healthy` и отсутствие ошибок импорта. Откройте [Airflow](http://localhost:8081), логин `admin`. Пароль создаётся при первом запуске и хранится в локальном томе; получить его можно командой:

```bash
docker compose exec -T airflow python -c 'import json; print(json.load(open("/opt/airflow/state/simple_auth_manager_passwords.json.generated"))["admin"])'
```

Учётная запись Airflow предназначена для управления ETL и не заменяет вход пользователя приложения. Пароль и содержимое тома `airflow_state` не включаются в репозиторий.

1. Включите DAG `bionicpro_daily_reports`: новый DAG изначально приостановлен. Планировщик создаст запуск за последний завершённый день.
2. Через ручной запуск задайте `report_date = 2026-11-08`, затем аналогично `2026-11-09` и `2026-11-10`. Для каждого дня дождитесь `success` у всех шести задач.
3. Проверьте опубликованные периоды и строки:

```bash
docker compose exec -T clickhouse sh -c 'clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --multiquery' < airflow/check_reports.sql
```

Ожидаемые дневные итоги:

| День | Пользователь | Протез | Движений | Среднее время, мс |
|---|---|---|---:|---:|
| 2026-11-08 | user1 | № 1, DEMO-Hand-A | 2 | 80 |
| 2026-11-08 | user2 | № 3, DEMO-Hand-A | 1 | 105 |
| 2026-11-10 | user1 | № 1, DEMO-Hand-A | 3 | 100 |
| 2026-11-10 | user1 | № 2, DEMO-Hand-B | 2 | 70 |
| 2026-11-10 | user2 | № 3, DEMO-Hand-A | 3 | 100 |

Для 9 ноября ожидаются запись готовности и ноль строк витрины. Повторите ручной запуск за 10 ноября: версия публикации изменится, показатели останутся прежними. Для поздних событий повторно обрабатывается их день.

Изменения `airflow/dags` подхватываются через подключённую папку. Изменения Dockerfile, зависимостей и стартового скрипта требуют пересборки.

### 4. API и интерфейс

```bash
docker compose up -d --build --wait api frontend
docker compose ps
curl -fsS http://localhost:8000/health
```

Ожидается `{"status":"ok"}`. Проверка `/health` читает структуру витрины под ролью API; она не проверяет аутентификацию и содержимое отчёта.

| Сервис | Адрес |
|---|---|
| Приложение | [localhost:3000](http://localhost:3000) |
| Keycloak | [localhost:8080](http://localhost:8080) |
| Документация API | [localhost:8000/docs](http://localhost:8000/docs) |
| Airflow | [localhost:8081](http://localhost:8081) |

Адреса frontend берутся из `frontend/.env` при сборке. После изменения кода или этого файла выполните `docker compose up -d --build frontend` и обновите страницу. API, Airflow и ClickHouse публикуют свои порты только на `127.0.0.1`; исходные порты frontend и Keycloak сохранены.

## API и ограничение доступа

```http
GET /reports?date_from=2026-11-08&date_to=2026-11-10
Authorization: Bearer <access_token>
```

Обе даты обязательны и включительны, сутки — UTC. Максимум 31 день и 10 000 строк за запрос. Отчёт содержит `status`, `timezone`, `period`, `row_count` и `items`; каждая строка — дата, протез, модель, число движений и среднее время реакции. Формат выгрузки — JSON.

| Ситуация | Ответ |
|---|---|
| Весь период готов, собственные данные есть | `200`, `status: ready`. |
| Весь период готов, собственных событий нет | `200`, `status: empty`, `row_count: 0`, `items: []`. |
| Хотя бы один день не опубликован или ещё не завершён | `409 / period_not_ready`, список `missing_dates`. Частичный отчёт не выдаётся. |
| Нет действительного access-токена | `401 / unauthorized`. |
| Неверный диапазон, формат дат или лишний параметр | `422 / invalid_request`. |
| Результат превышает лимит строк | `413 / report_too_large`; нужно сократить период. |
| ClickHouse или получение ключей Keycloak недоступны | `503`; ошибка не подменяется пустым отчётом. |

Сервер проверяет подпись RS256, доверенный `iss`, audience `reports-api`, срок действия, обязательные поля, тип `Bearer` и `azp = reports-frontend`. Ключи JWKS берутся с настроенного сервером адреса. Владелец определяется по проверенным `iss` и `sub`. Эти значения входят в параметризованный SQL вместе с периодом и опубликованными версиями.

API принимает только `date_from` и `date_to`. Параметры `user_id`, `owner_subject`, `owner_issuer`, `client_id` и `prosthesis_id` отклоняются с `422`. Произвольные заголовки владельца игнорируются. Роли пользователя не дают исключения из проверки принадлежности. ID-токен и refresh-токен не принимаются вместо access-токена.

API обращается только к ClickHouse под `reports_reader`, без записи и без доступа к исходным CRM/телеметрии. Пользовательский ответ имеет `Cache-Control: no-store`; имя файла передаётся в `Content-Disposition`. CORS разрешает только origin приложения. Рабочий процесс API запускается под UID 10001.

### Поведение интерфейса

Форма позволяет выбрать до 31 завершённого дня. Начальное значение — вчерашний день UTC по часам браузера; готовность подтверждает сервер. Во время запроса поля и повторное нажатие блокируются.

Перед запросом вызывается `keycloak.updateToken(30)`, затем берётся актуальный access-токен. При `401` допускается одно принудительное обновление `updateToken(-1)` и один повтор. При повторном отказе предлагается войти заново. Запрос API ограничен 30 секундами, отправляется без cookies и с запретом кеширования и перенаправлений.

Успешный JSON скачивается через временный Blob URL, который затем освобождается. Для `empty` показывается отдельное сообщение об обработанном периоде без телеметрии. При `409` отображаются неподготовленные даты, скачивание не начинается. Ошибки сети и сервиса также выводятся на странице. Обновление токена и владение данными не определяются введённым логином.

python3 -m unittest discover -s airflow/tests -v

Проверены 17 тестов ETL, 18 тестов API и 18 тестов frontend. Тесты покрывают дубли, ошибки связей, сбои до публикации, повторную обработку, готовность всего периода, проверку JWT, ограничение владельца, даты, обновление токена и скачивание. В модульных тестах внешние сервисы заменены управляемыми объектами; подпись JWT проверяется с тестовым RSA-ключом.

### Проверка доступа на работающем стенде

После подготовки учебных дней:

```bash
python3 scripts/check_report_access.py --day 2026-11-10
```

Скрипт входит под двумя реальными пользователями через Authorization Code + PKCE S256, сверяет полный набор строк и проверяет попытки подмены. Используются учебные пароли из realm; токены находятся только в памяти. Для каждого пользователя создаётся отдельная сессия, которая закрывается в конце. Скрипт рассчитан на локальные адреса и форму Keycloak 21.1 без дополнительных действий при входе.

Подтверждённые результаты:

| Проверка | Результат |
|---|---|
| `user1`, 8–10 ноября | Три строки по двум собственным протезам, семь движений. |
| `user2`, 8–10 ноября | Две строки по одному собственному протезу, четыре движения. |
| Нет токена или JWT некорректен | `401`, без данных отчёта. |
| Изменён `sub` без новой подписи | `401` для обоих пользователей. |
| ID-токен или refresh-токен вместо access-токена | `401` для обоих пользователей. |
| Пять параметров владельца/протеза подменены по отдельности | `422` для обоих пользователей. |
| Подменены `X-User-Id` и `X-Owner-Subject` | Каждому возвращён прежний собственный отчёт. |

### Проверка через интерфейс

Войдите в приложение под `user1` и выполните три запроса:

| Период | Подтверждённый результат |
|---|---|
| 08.11.2026 — 10.11.2026 | Скачанный JSON содержит `ready`, UTC, три строки и семь движений. |
| 09.11.2026 — 09.11.2026 | Скачанный JSON содержит `empty`, UTC, ноль строк и пустой `items`. |
| 07.11.2026 — 10.11.2026 | Форма сообщает о неготовности и указывает `2026-11-07`. Для воспроизведения этот день не должен быть опубликован DAG. |

Дополнительно можно проверить неверный диапазон и сменить пользователя кнопкой «Выйти». Содержимое файла проверяется в загрузках браузера. При работе через Swagger UI нажмите **Authorize**, используйте `client_id = reports-frontend` без `client_secret`, войдите через Keycloak и выполните `GET /reports`. Фактический ответ скачивается по **Download file** в разделе **Server response**; **Example Value** — пример схемы.

Access-токен учебного realm действует 300 секунд. В форме приложения он обновляется адаптером; в Swagger после истечения нужно выполнить **Authorize → Logout → Authorize**. При фиксации результатов достаточно статуса и тела ответа; токены и пароли не публикуются.

### PKCE и выполнение по расписанию

В DevTools → Network при входе присутствуют `code_challenge_method=S256` и `code_challenge`, а в обмене кода — `grant_type=authorization_code` и `code_verifier`. Успешный обмен возвращает HTTP 200.

Отрицательная проверка без PKCE:

```bash
curl -sS --max-time 15 -D - -o /dev/null --get 'http://localhost:8080/realms/reports-realm/protocol/openid-connect/auth' --data-urlencode 'client_id=reports-frontend' --data-urlencode 'redirect_uri=http://localhost:3000/' --data-urlencode 'response_type=code' --data-urlencode 'response_mode=query' --data-urlencode 'scope=openid' --data-urlencode 'state=pkce-negative-test'
```

Подтверждён отказ HTTP 302: в `Location` возвращаются `error=invalid_request` и описание `Missing parameter: code_challenge_method`.

У DAG подтверждены успешные плановые запуски 12–14 ноября 2026 года. Запуск `scheduled__2026-11-14T00:00:00+00:00` обработал 13 ноября. Ручные запуски за 8–10 ноября также успешны. Повторная обработка 10 ноября сохранила три строки и восемь движений для всех клиентов; версия публикации изменилась. Пустой день 9 ноября присутствует в реестре. Актуальные запуски доступны в Airflow или через CLI:

```bash
docker compose exec -T airflow airflow dags list-runs bionicpro_daily_reports --limit 10
```

## Ограничения стенда

- Это локальное учебное развёртывание с HTTP и демонстрационными паролями. Целевая схема предусматривает HTTPS, серверное хранение токенов и изоляцию данных по странам.
- Реальные CRM, устройства, мобильный клиент и внешние IdP не подключены. Учебные данные и привязка пользователей описаны выше.
- Airflow работает в режиме `standalone` с LocalExecutor. Автоматическая очистка версий, резервное копирование и развёртывание высокой доступности не реализованы.
- Исходные версии Node 16 и Keycloak 21.1 сохранены для совместимости с проектом. Сборка frontend проходит с предупреждениями исходных пакетов `@react-keycloak`, Browserslist и `babel-preset-react-app`; проверка успешной сборки не означает проверку зависимостей на все известные уязвимости.
